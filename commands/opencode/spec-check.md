---
description: "Check the execution tool's design output against the OpenSpec proposal + delta specs (usage: /spec-check <change-id>)"
---

Arguments: $ARGUMENTS

Check the execution tool's design output against an OpenSpec change (handoff-driven schema). This is the only plan-vs-spec check: every delta requirement and scenario is planned, nothing is planned without a source or against the delta, and the plan cites requirements by name instead of restating them.

1. Pick the change: the id given, else the single active change from `openspec list --json` (ask if several).
2. Run `node .openspec-handoff/scripts/spec-check.mjs <change-id> --write`. It reads `proposal.md`, the delta specs and the tool's planning output (AI Hero: `execution/spec.md` user stories + `execution/tickets/`; Superpowers: `execution/plan-<change-id>.md` tasks), and writes `execution/spec-check.md` with the coverage table and the mechanical findings: **Missing** (requirement no unit names / scenario no unit mentions), **Unknown references** (a unit names a requirement or scenario that is not in the delta), **Added without source** (a story / ticket / task that names no delta requirement). It also lists **Spec changes since the last check**: requirements / scenarios added, changed, removed or renamed since the last **accepted PASS** (hashes in `execution/.spec-check.json`), each with the stories / tickets / plan tasks citing it (report-only; never a gap by itself). The list stays on every run until a PASS is accepted (step 8).
3. Agent review (your judgement): read `proposal.md`, every delta and each unit the report lists. Replace the comment under `### Agent review` in `execution/spec-check.md` with these four lists, one bullet per finding (`<file>:<line> <unit> vs "Requirement: <name>" / Scenario "<name>": <what>`) or `- none`:
   - **Missing**: behaviour a requirement or scenario needs that the unit naming it does not plan (a dropped branch, error case or value).
   - **Invented**: behaviour a unit plans that no requirement or scenario asks for, or work the proposal puts out of scope.
   - **Contradicted**: a unit plans different behaviour from the requirement it names (different values, a different error type, a different order).
   - **Restated (advisory)**: a unit that restates requirement or scenario text instead of citing it by name - suggest the citation. Never changes the result.
4. Set the `### Result` line. The script writes `GAPS: ...` when a mechanical check failed, otherwise `PENDING: ...`. Replace PENDING: Missing, Invented and Contradicted all `- none` -> write exactly `PASS`; any finding there -> `GAPS: <n> agent finding(s)`. A mechanical GAPS line stays GAPS. Never leave PENDING in the saved report.
5. Line estimate after planning (warn-only; the ~300-line budget is checked only here - the split gate counts requirements and capabilities): every ticket / plan task should carry an `Estimate: ~N lines` line (code + tests). The report's "Size" section totals them against the budget; over it, suggest re-splitting with `/split-check <change-id>` (a slice is re-split into its existing parent, a whole change gets its own parent; /split-apply builds the new slice ids, continuing the numbering) before implementation. It never blocks.
6. Spec changes: if the section lists any, tell the engineer the one order: (delta edited, `openspec validate <change-id> --strict` passed) -> re-plan ONLY the open units the report names with the tool's planning -> /spec-check again until PASS. Done units (ticket `Status: done`, task with every step ticked) are never touched: a change affecting done work becomes a new ticket / plan task. Where a planned decision changed, the planning output notes `superseded by delta edit: <reason>`; the design session file (grill.md / brainstorm.md) stays as-is - the delta wins. Do not edit the tool's files yourself unless asked.
7. Show the report. On **GAPS**: stop. Fix the design output (cite the requirement by name; drop unsourced or invented work; fix contradictions) - or, if the design found real missing behaviour, update the delta first, then follow the one order in step 6 (`openspec validate <change-id> --strict` -> /spec-check lists the changes and the units citing them -> re-plan only those - see "Updating tool files" in the wrapper skill -> /spec-check until PASS). On **PASS**: go to step 8; planning is done after it; the engineer starts implementation with the tool's own command recorded as `apply_mode` in `handoff.md`.

8. **Accept PASS** (only when the saved Result is exactly `PASS`): run `node .openspec-handoff/scripts/spec-check.mjs <change-id> --accept`. It records the current delta as the baseline in `execution/.spec-check.json` (it refuses on GAPS, PENDING or a delta edited since the report) and does not rewrite the report. Commit `execution/.spec-check.json` with the planning files. Until a PASS is accepted, every /spec-check run keeps listing the spec changes.

Do not restate requirement text in the report; name requirements and scenarios.
