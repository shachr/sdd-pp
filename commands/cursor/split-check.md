---

Arguments: <change-id> as given after the command.

Split gate for an OpenSpec change (handoff-driven schema). Runs automatically at the end of the specs stage, before /handoff; rerun it any time (also on a slice, to re-split it into the same parent). Warn-only: it never fails a change. Nothing is split without the engineer's approval.

1. Pick the change: the id given, else the single active change from `openspec list --json` (ask if several). If it is a split parent (has `slices.md`), run `node .openspec-handoff/scripts/split-check.mjs <id>` and `node .openspec-handoff/scripts/sdd.mjs split next <id>` (= `/split-next <id>`), show both and stop.
2. Run `node .openspec-handoff/scripts/split-check.mjs <id> --write`. It counts the delta requirements and capabilities (no line estimate here - the ~300-line estimate comes after planning, in /spec-check, from the tool's tickets / plan; the real diff is measured at the PR by check-handoff).
   - **fits** (at most 5 requirements and 2 capabilities): one line. Say nothing more and continue to /handoff.
   - **WARNING** (more): go on.
3. **Propose slices** in `execution/split-proposal.md`: front matter with `approved_by:` left empty, then `## Slices`, one `### Slice: <slice>` block each - the slice part only, e.g. `core`; `/split-apply` names the change `<parent>-<nn>-<slice>` (`add-text-stats-01-core`) - with `- order:` (two digits: `01` first, `02`, ...; the flag cleanup slice uses `99`; on a re-split leave it out and the numbering continues after the parent's highest), `- goal:`, `- capabilities:`, `- requirements:` (exact names, `;`-separated), `- depends_on:` (`none`, or slice parts from this proposal / full ids of existing slices), `- flag:` (`none`, or a flag name only when the slice gates user-visible behaviour that must stay off until a later slice lands), `- removes_flag:` (the cleanup slice - always plan one when any slice has a flag, depending on the flagged slice). To cut one requirement in two use `- split: <original name> -> <new name> [<scenario>; <scenario>]` in each receiving slice. Names only: no SHALL/MUST or WHEN/THEN. Aim for at most 5 requirements per slice, few dependencies, and slices on different capabilities so they can run in parallel.
4. Rerun `split-check.mjs <id> --write`; it lints the proposal and shows the slices, which are ready first and which pairs are parallel-safe (no dependency, no shared capability). Show that report to the engineer and **STOP**: they approve or edit. Never split on your own.
5. After approval (the engineer's, or yours on their behalf only if they delegated it - say so in `approved_by:`): commit the change's deltas (that commit is the loss-check baseline, read later with `git show`), then run `/split-apply <id>` (`node .openspec-handoff/scripts/sdd.mjs split apply <id>`). It builds the ids `<parent>-<nn>-<slice>` and refuses a full id that does not match (it prints the expected name). The original change becomes the **parent** (schema `split-plan`, a control plane: why/scope in proposal.md, and `slices.md` with each slice's id, goal, capabilities, depends_on, flag, ticket, status and the `split_commit`; **no requirement or scenario names**). Each slice becomes a handoff-driven child with the original requirement blocks copied verbatim and an empty `## Split notes` section in its proposal.md. Keep the parent's proposal.md free of requirement names (the loss check fails on any).
6. Finish the children. Every deliberate difference from the original goes into the `## Split notes` of the child that made it, one line each:
   - `- dropped: Requirement|Scenario "<original name>" - <why>`
   - `- added: Requirement|Scenario "<new name>" - <why>` (e.g. the flag requirement)
   - `- renamed_from: Requirement|Scenario "<original name>" -> "<new name>" - <why it is the same behaviour>`
   - `- split_from: Requirement "<original name>" - confirmed` (after narrowing a cut requirement; it keeps its `<!-- split_from: ... -->` line)
   The cleanup slice writes `## REMOVED Requirements` for the flag.
7. `node .openspec-handoff/scripts/split.mjs loss <parent>` must PASS: every original requirement and scenario (from the split commit) is in exactly one child or covered by a split note; nothing duplicated or unsourced; no original names in the parent. When an original name has no match it lists **Possible renames** - unmatched originals next to child names with no original. Judge semantic equivalence yourself: if a pair is the same behaviour, record `renamed_from` in that child's split notes; otherwise restore the original or record `dropped`.
8. `openspec validate --all --strict`, then commit the parent and every child (proposal + specs only) as ONE planning PR. `/split-next <parent>` writes `tickets/<slice>.md` (Jira-pasteable, no requirement names) for READY slices.
9. Engineers take READY slices: `/split-mark <parent> <slice> in-progress` (committed on main - the next report trusts this mark), a branch from main, a short design session that reads the parent's `execution/grill.md` / `brainstorm.md`, `/handoff <slice>` and the printed next steps. A slice is **done** when its archived folder is on main: the archive is committed in the slice's own PR with its code. After each merge rerun `/split-next <parent>`. When all are done: `/split-archive <parent>` (final loss check, then `openspec archive <parent> --skip-specs -y`; never sync specs from, or verify, the parent - `/opsx:archive` cannot pass `--skip-specs`).
